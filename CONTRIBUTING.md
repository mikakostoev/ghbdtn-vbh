# Contributing

Contributions are welcome in English or Russian. The short version: `./test.sh` must stay green, and the app must
stay free of networking code.

## Getting started

```bash
git clone https://github.com/mikakostoev/ghbdtn-vbh.git && cd ghbdtn-vbh
./build.sh && open "ghbdtn vbh.app"
```

Xcode or the Command Line Tools, macOS 13+. Tasks for a first contribution are labelled
[good first issue](https://github.com/mikakostoev/ghbdtn-vbh/labels/good%20first%20issue) — pick any and
leave a comment saying you took it.

## What to check before a PR

- `./test.sh` — build, self-test and the runs on the test texts. `Tests/chat-*.txt` and `Tests/common-*.txt` must
  stay at **0 false switches**; if you changed the switching rules, attach the output before and after.
  `common-xx` and `stress-xx` are the languages without a system dictionary (Finnish, Icelandic, Norwegian,
  Polish, Lithuanian, Hebrew, Croatian, Slovak, Estonian, Macedonian, Albanian, Serbian, Farsi, Georgian), where
  the tables decide alone. `--selftest` prints the spellers this Mac has; the set differs between macOS versions.
- `Tests/live.sh` — live typing into a test window, if you touched the code around keyboard events or text
  replacement.
- A new rule or a fixed case — add an example to the self-test (`--selftest`, in `Layouts.swift`) so it doesn't
  break again.

## What is not accepted

- **Networking code** of any kind: updates, statistics, crash reports. It is the README's main promise, and it
  is checked with one `grep`.
- Writing typed text to disk, beyond the three existing files in Application Support.
- New dependencies: the project lives on a single `Package.swift` with no packages, and that stays.
- Binary files on `main`. The site's `demo.gif` and its two icons live with the site, on the `landing` branch,
  and the gif is regenerated by `Tools/demo.sh`; the app icon is drawn by `Tools/icon.swift`.

## Releasing

Merging to main is releasing: every push to main that touches the app (`Sources/`, `Resources/`, the build
scripts) is tagged with the next patch version by the release workflow once the test workflow has passed on it;
the release workflow builds the universal zip with `release.sh` and attaches it to the GitHub release, and the
cask workflow then points `Casks/ghbdtn-vbh.rb` at it.
Docs-only changes release nothing. For a minor or major version, `git tag v2.1.0 && git push origin v2.1.0`
on main (or "Run workflow" on the Actions page with the version typed in) does the same for that number, and
patch releases continue from it. The build is
ad-hoc-signed until `DEVELOPER_ID_P12` is set; once it is, the other four secrets listed at the top of
`.github/workflows/release.yml` must be set too, or the run fails — with all five, the same tag comes out
signed with a Developer ID, notarized and stapled, and macOS opens it without "Open Anyway". Nothing in the
app changes either way. When those secrets are added, the first-launch/"Open Anyway" notes in `README.md` and in
`index.html` on the `landing` branch need updating too — they currently say the app is unsigned.

## The site

The site is not in `main`: it is the `landing` branch, and Pages publishes that branch as it is. Edit
`index.html` there — one static page, no build step, no dependencies, and no test run. Everything in that branch
becomes a published URL, so the app's source stays here. The plans and specs under `docs/superpowers/` also stay
here: they are the record of how the project was built, not the site.

## How the code is laid out

About a thousand lines in `Sources/ghbdtnvbh/` (not counting the generated `Trigrams.swift`), readable in an
evening:

| File | Responsibility |
|---|---|
| `main.swift` | Event tap, menu bar, replacing the word on screen |
| `Buffer.swift` | The current word and a couple of previous ones; when the buffer is cleared |
| `Layouts.swift` | Layouts, the rules for "this word was typed in the wrong layout", dictionary and trigrams |
| `Trigrams.swift` | Letter-combination frequency tables and one-letter words for 35 languages; generated by `Tools/trigrams.py`, never edited by hand |
| `Words.swift` | Slang and abbreviations the system dictionary doesn't know |
| `Settings.swift` | Settings window and the files in Application Support |
| `Eval.swift` | `--selftest` and `--eval` |

Style: short functions, comments about "why" rather than "what". A `// ponytail:` comment marks a deliberate
simplification and hints at how to grow it if needed.

## A new language

The switcher works with any macOS layout: the language comes from the layout itself, words are checked by the
system dictionary and the letter-combination table. Tables exist for 35 languages (`LANGS` in
`Tools/trigrams.py`). To add one more:

1. Download `xx_50k.txt` from FrequencyWords (it has to be the full 50,000-word list; shorter ones make a
   patchy table), add the language code to `LANGS` — the one macOS reports for the layout (`Layout.lang`) — and
   run `python3 Tools/trigrams.py`. It works out the alphabet and the one-letter words itself.
2. Test texts: `Tests/chat-xx.txt` from real chat, or at least `common-xx.txt` and `stress-xx.txt` cut from the
   same frequency list (every 8th word of the first 2,000; every 15th past rank 5,000), and a line for the layout
   in the loops in `test.sh` and `test.yml`. For a language without a system dictionary this is the only check.

## A bug with a particular app

The most valuable reports are "in app X the word isn't replaced / the wrong thing is replaced". Give the macOS
version, the app's name and what was typed; if the app is Electron-based or a browser, say which.
